Friend setup guide

A detailed runbook for setting up one friend with Beachcar: TestFlight access, Clerk and Beachcar provisioning, initial preferences, remote automation, and AI payment choices.

Last updated: 2026-06-26. Current deployed Worker: https://beachcar-watch.jon-cooper.workers.dev.

Fast Path

  1. Confirm the deployed Worker and TestFlight build are healthy.
  2. Decide how AI will be paid for this friend: owner-managed Gateway, friend-run cloud agent, owner Codex push, BYOK alias, or deterministic no-paid-AI.
  3. Add the friend to TestFlight, or create an external testing group if they should not be an App Store Connect internal user.
  4. Sign in to the Beachcar PWA as an owner and create a Beachcar invite code for the friend's exact sign-in email.
  5. Send the friend the TestFlight invite/link, PWA URL, invite code, and the AI/automation instructions for the mode you chose.
  6. Have the friend sign in, accept the invite code, complete onboarding, and open the iOS app with the same Clerk identity.
  7. If they will run their own automation, have them open Preferences, create an automation token, download the Beachcar skill, and connect their cloud agent to the hosted MCP endpoint.

Preflight Before Inviting

Run these from the repo root before you send a friend a setup message. These checks do not need to reveal any secret values.

git status --short --branch
bun run preflight
bun run cloudflare:check
bun run ios:asc:check

Expected result for the current branch:

  • git status --short --branch should show codex/remote-mcp-friend-automation and ideally no uncommitted changes except deliberate doc edits.
  • bun run preflight should pass typecheck, tests, service-worker syntax, deploy readiness, and client build.
  • bun run cloudflare:check should report the Worker, D1, R2, and required secrets. A warning for optional BEACHCAR_AI_GATEWAY_TOKEN is acceptable only if you are not testing owner-managed AI scoring.
  • bun run ios:asc:check should find the Beachcar App Store Connect app, bundle id com.joncooper.beachcar, and TestFlight group Beachcar Internal.
Do not give the friend these secrets: PUBLISH_TOKEN, CLERK_SECRET_KEY, Cloudflare API tokens, App Store Connect API keys, or raw OpenAI/OpenRouter provider keys.

If you need to deploy an app update

The guarded rollout path validates env, couples the production D1 name and UUID, proves rollback availability, captures private recovery evidence, runs a strict keep-vars dry run, applies only the expected migration, deploys the Worker and supplied secrets atomically, and verifies the remote surface. Direct bootstrap and remote-migration shortcuts are disabled.

bun run deploy:remote -- --dry-run
bun run deploy:remote -- --execute --yes
bun run cloudflare:verify
bun run cloudflare:check

When BEACHCAR_RUNNER_MODE=deterministic, the rollout skips Cloudflare Container image publishing. Only add --deploy-containers when intentionally testing the Codex/browser-heavy Container path.

Required Worker secrets

  • PUBLISH_TOKEN - owner/admin import and invite operations.
  • CLERK_SECRET_KEY - Clerk Backend API validation.
  • CLERK_JWT_ISSUER - Clerk issuer URL, usually https://...clerk.accounts.dev.

Optional Worker secrets for owner-paid AI

  • BEACHCAR_AI_GATEWAY_TOKEN. CLOUDFLARE_API_TOKEN is deployment authentication only and is never used as a Worker runtime AI credential.
  • BEACHCAR_AI_GATEWAY_BASE_URL, or CLOUDFLARE_ACCOUNT_ID plus BEACHCAR_AI_GATEWAY_ID.
  • BEACHCAR_AI_GATEWAY_MODEL, using the model id expected by the selected provider.
  • BEACHCAR_AI_ESTIMATED_MICROS_PER_1K_TOKENS, if Gateway/provider responses do not return exact cost.

If the dedicated Gateway token is absent, the guarded rollout explicitly reports heuristic-only mode and the first friend pilot can proceed without paid AI scoring.

Clerk Setup

Clerk owns identity. Beachcar owns friend access. That means the friend signs into Clerk first, then Beachcar decides whether that signed-in email is invited, active, or disabled.

Clerk dashboard checks

  1. Open the Clerk dashboard and select the Beach Car Watch app.
  2. Confirm Google sign-in is enabled for the web and native app sign-in flow.
  3. Confirm the publishable key in .env.local and .deploy.env matches this Clerk instance.
  4. For iOS, confirm Clerk Native API is enabled and the native application is configured for bundle id com.joncooper.beachcar.
  5. Confirm the iOS Associated Domain used by the app is still valid. Current local docs mention webcredentials:brief-coyote-47.clerk.accounts.dev.

Beachcar invite behavior

  • Any signed-in non-owner user is created as invited.
  • The owner creates an invite from https://beachcar-watch.jon-cooper.workers.dev/?admin=1.
  • The invite code is single-use, stored as a hash, and must be accepted by the same email address used when the invite was created.
  • After invite acceptance, the friend becomes active and sees onboarding.
  • After onboarding, their profile, source settings, AI settings, feedback, runs, automation tokens, and usage ledger are scoped to their user id.

Create the Beachcar invite

  1. Open the Beachcar admin console.
  2. Paste your PUBLISH_TOKEN into the publish-token field. It is only kept in the browser tab.
  3. Enter the friend's exact email address. Use the same address they will use for Google/Clerk sign-in.
  4. Click Create invite.
  5. Copy the invite code and send it directly to the friend. Do not send the publish token.
  6. Click Refresh users after they sign in and accept the code.

TestFlight Setup

The current command-line build pipeline uses App Store Connect API-key authentication and Xcode automatic signing. The latest uploaded build should already be in the Beachcar Internal group.

Current build check

bun run ios:asc:check

Current expected values:

  • App: Beachcar
  • Bundle ID: com.joncooper.beachcar
  • Internal group: Beachcar Internal
  • Latest uploaded build: 0.1.0 (202606252208)

Internal tester path

Use this when the friend can be added as an App Store Connect user. It is fastest because internal testing usually avoids the external beta review loop.

  1. Open App Store Connect.
  2. Add the friend under Users and Access with the least access that still allows internal TestFlight testing.
  3. Open Apps - Beachcar - TestFlight - Internal Testing.
  4. Add the friend to Beachcar Internal, or confirm the group has access to the latest build.
  5. Ask the friend to install Apple's TestFlight app and accept the invite email.

External tester path

Use this when the friend should not have App Store Connect access. This is the more realistic outside-friend path, but Apple may require beta app review before external testers can install a build.

  1. Create an external testing group in App Store Connect - Apps - Beachcar - TestFlight - External Testing.
  2. Switch future uploads to external-eligible builds by setting TESTFLIGHT_INTERNAL_ONLY=NO in your local ignored .env.apple.local.
  3. Upload a new build with bun run ios:release.
  4. Attach the build to the external group and complete any required Beta App Review metadata.
  5. Send the TestFlight public link or invite email after Apple marks the build available for external testing.

Upload a new build if needed

bun run ios:build
bun run ios:archive
bun run ios:testflight

Or run both archive and upload:

bun run ios:release

Each upload needs a new build number. If omitted, the archive script uses a timestamp build number.

Friend Onboarding

What to send

Send one message with the following items:

  • TestFlight invite or public link.
  • PWA URL: https://beachcar-watch.jon-cooper.workers.dev.
  • Beachcar invite code.
  • The sign-in email they must use.
  • Which AI mode they should select during onboarding.
  • If they will run their own automation, instructions to create an automation token and download the Beachcar skill after onboarding.

Friend steps

  1. Install TestFlight from the App Store and accept the Beachcar TestFlight invitation.
  2. Open the PWA URL in Safari or Chrome and sign in with Google using the invited email.
  3. Enter the Beachcar invite code at the invite gate.
  4. Complete onboarding: name, region, budget ceiling, stretch room, taste calibration, avoid notes, source toggles, notification preference, and AI mode.
  5. Install/open the iOS TestFlight build and sign in with the same email.
  6. Confirm the iOS app either shows the latest run or a no-listings state instead of the invite gate.
  7. Use feedback controls in the iOS app or PWA: like, star, hide, avoid, and freeform notes. These feed future runs.

First smoke test as the owner

  1. Open the admin console and refresh users. Confirm the friend is active and onboarded.
  2. Ask the friend to open Preferences and confirm their AI mode and daily/monthly caps.
  3. Use Run Now if the friend has budget and owner-managed/heuristic workflow is acceptable.
  4. Open Run detail and check listings, sources, AI provider/status, cost, and runner tasks.
  5. Confirm the same latest run appears on iOS.

AI Options

There are several valid operating modes. Pick one deliberately for each friend. Do not assume a ChatGPT or Codex subscription pays for backend API calls.

Mode Who pays Best for Beachcar tracking
Deterministic / no paid AI Owner pays only Cloudflare Worker, D1, R2, and bandwidth/storage. First smoke test, source-cache-only runs, proving onboarding and app UX. No provider spend unless external automation records usage.
Owner-managed AI Gateway Owner pays via Cloudflare AI Gateway plus the configured model provider or Cloudflare billing route. Best first paid beta mode because you control budgets centrally. Worker records provider, model, tokens, request id, estimated/actual cost, daily/monthly budgets.
Friend BYOK via Gateway alias Depends on how the Gateway provider key is configured. The friend can be the provider-key payer, but Beachcar only stores a Gateway alias, not the raw key. Later beta with trusted friends who want their provider account charged. Same as managed mode, with gatewayKeyRef and cf-aig-byok-alias.
Friend-run cloud agent through hosted MCP Friend pays for their chosen cloud agent, Codex/Claude subscription, browser harness, and any model/API calls inside that environment. Friends who want self-serve research automation without you running a scraper or sharing your AI keys. MCP record_usage logs what the agent reports. Provider-side payment remains outside Beachcar.
Owner Codex pushing runs Owner pays with local Codex subscription/API/harness and publishes data into Beachcar. White-glove setup, debugging a friend's preferences, or one-off research runs. Track usage manually through MCP record_usage or admin usage ingestion if not using MCP.
Cloudflare Codex integration Cloudflare account/credits route the Codex CLI through AI Gateway. It is not the same as using a ChatGPT subscription for backend API calls. Experimenting with Codex through Cloudflare AI Gateway, not the default Beachcar backend path. Only applies if the runner/agent is configured to use that integration and record usage back to Beachcar.

Recommended first friend choice

For a real friend beta, start with deterministic/no paid AI or owner-managed AI Gateway with tight caps. Use friend-run hosted MCP when the friend is comfortable driving their own cloud agent. Defer BYOK until you want to operationalize provider-key aliases and support.

Configure owner-managed AI Gateway

  1. Open the Cloudflare dashboard and create or select an AI Gateway for Beachcar.
  2. Choose a provider path. Cloudflare documents native OpenAI and OpenRouter provider endpoints.
  3. Configure provider credentials or Cloudflare's supported provider-token mechanism in the Gateway/account.
  4. Set Beachcar deploy env values in ignored .deploy.env and/or Worker secrets: 
    BEACHCAR_AI_GATEWAY_TOKEN=...
BEACHCAR_AI_GATEWAY_BASE_URL=https://gateway.ai.cloudflare.com/v1/<account_id>/<gateway_id>/openai
BEACHCAR_AI_GATEWAY_MODEL=openai/gpt-4.1
BEACHCAR_AI_ESTIMATED_MICROS_PER_1K_TOKENS=2000
  5. For OpenRouter through Gateway, use the OpenRouter Gateway v1 endpoint and a model id supported by OpenRouter: 
    BEACHCAR_AI_GATEWAY_BASE_URL=https://gateway.ai.cloudflare.com/v1/<account_id>/<gateway_id>/openrouter/v1
BEACHCAR_AI_GATEWAY_MODEL=<openrouter-model-id>
  6. Run bun run deploy:env:check, then deploy intentionally with bun run deploy:remote -- --execute --yes.
  7. Ask the friend to select Managed in onboarding/Preferences and set low daily/monthly caps.
  8. Queue a run and check Run detail - AI plus Preferences - usage summary.

Configure friend BYOK via Gateway alias

  1. Do not ask the friend to paste sk-..., sk_proj..., sk_..., or session-style provider keys into Beachcar. The app rejects raw-looking provider keys.
  2. Create a provider-key alias through Cloudflare AI Gateway or the supported secret/provider-key mechanism.
  3. Give the friend only the alias/reference value, not the raw key.
  4. Ask the friend to choose BYOK and paste the alias into the AI Gateway alias field.
  5. Keep daily/monthly budget caps set even for BYOK. Beachcar budgets gate app-run creation, but the actual provider account is still the source of truth for spend.

Configure friend-run hosted MCP

  1. After onboarding, the friend opens Preferences - Connect automation.
  2. They click Create token. The token is shown once. If lost, revoke it and create a new one.
  3. They click Download skill. The downloaded SKILL.md contains the deployed MCP endpoint.
  4. Their cloud agent should connect to https://beachcar-watch.jon-cooper.workers.dev/mcp with Authorization: Bearer <token>, or use OAuth protected-resource discovery if supported.
  5. The agent should call get_setup_context, plan_daily_research, search_bat_cache, publish_run, record_usage, and verify_latest_run.
  6. The friend can revoke manual tokens and OAuth connections from Preferences.

Codex Streamable HTTP MCP config example for a friend-owned environment:

[mcp_servers.beachcar]
url = "https://beachcar-watch.jon-cooper.workers.dev/mcp"
bearer_token_env_var = "BEACHCAR_MCP_TOKEN"

Then the friend stores their token as BEACHCAR_MCP_TOKEN in that cloud environment. If the client supports OAuth, use the hosted metadata instead of a manually copied token.

Configure owner Codex pushing

Use this when you want to do the research for a friend from your own Codex environment and publish into their Beachcar account.

  1. Use the friend's profile and feedback from Beachcar as the prompt/context.
  2. Prefer the friend's hosted MCP token when possible so the run, usage events, and automation activity log are user-scoped without using the owner admin token.
  3. If using the admin import path, publish to the user-specific import route rather than the legacy owner-only route.
  4. Record AI/browser usage through MCP record_usage or the admin usage ingestion endpoint so the friend and owner can see cost attribution.
  5. Verify with verify_latest_run, then ask the friend to open the iOS app.

Source Gathering

Beachcar has two source patterns today.

  • Bring a Trailer cache first: BaT public RSS candidates are ingested into D1 every 15 minutes and are available through admin source-cache controls and MCP search_bat_cache.
  • Browser-capable agent for rendered sources: Cars & Bids and other rendered/fragile sites should be handled by a user-authorized browser/cloud-agent environment when needed.

Agents should respect source terms, rate limits, authentication boundaries, and bot controls. They should record blocked sources in sourceSummary rather than inventing listings.

Image Behavior

Runs published by Workflow, admin import, or hosted MCP all use the same image path.

  • Source image metadata is stored in D1.
  • The Worker mirrors originals into R2 as needed.
  • The Worker creates thumb at 320px, deck at 960px, and full at 1600px with WebP transformation where Cloudflare supports it.
  • Image responses use immutable cache headers.
  • The PWA service worker cache-firsts only /api/images/... responses and trims the image cache to 180 entries. Authenticated JSON API responses are not cached.
  • The iOS app uses an in-memory decoded image cache, a 256 MB disk URL cache, and prefetches up to 24 nearby images after a run loads.

Practical expectation: the first view of a new run may warm images; subsequent swipes should be much faster.

Verification Checklist

  1. Backend: bun run cloudflare:check reports Worker deployed, D1 migrated, R2 exists, required secrets set.
  2. Auth: Friend signs in with the invited email and accepts the invite code.
  3. Onboarding: Friend saves budget, region, taste, avoid notes, sources, AI mode, and caps.
  4. iOS: Friend opens the TestFlight build and sees the same account state as the PWA.
  5. Run: Run Now queues or the hosted MCP publishes a run; Run detail shows sources, listings, AI status, and cost.
  6. Images: First cards show deck image variants and become fast after prefetch/cache warmup.
  7. Automation: If used, Preferences shows the token/OAuth connection last-used time and recent automation events.
  8. Spend: For owner-managed AI, validate daily/monthly caps and Cloudflare AI Gateway logs before broad friend access.

Friendly Tester Feedback

For a broader public beta, collect concrete task feedback from each friendly tester. Avoid broad questions like "do you like it?" The highest-value feedback is where setup broke, where the result felt untrustworthy, where cost was unclear, and where the app failed to learn their taste.

Tester script

  1. Install Beachcar through TestFlight.
  2. Sign into the PWA, accept the Beachcar invite, and complete onboarding.
  3. Open the iOS app and confirm it shows the same account state as the PWA.
  4. Review one existing or generated run.
  5. Mark at least five listings with like, star, hide, or avoid.
  6. Change one preference after seeing the first results.
  7. Optional for technical testers: connect a cloud agent with the downloaded skill and publish a run through hosted MCP.
  8. Send screenshots of any confusing screen or error state.

Setup friction

  • How long did it take from invite to usable app?
  • Did TestFlight, Clerk sign-in, or the Beachcar invite code confuse you?
  • Did the web app and iOS app feel like the same account?
  • What was the first point where you almost stopped?
  • What device, iOS version, and browser were you using?

Preference quality

  • Did onboarding capture your actual taste?
  • Was budget, region, and stretch budget enough?
  • What constraints were missing: rust tolerance, title status, distance, manual/auto, seller type, no-reserve only, site exclusions, shipping willingness, or something else?
  • Which three vehicles are "show me more like this" examples?
  • Which three vehicles are "never show me this again" examples?
  • Did the taste calibration choices feel useful, too broad, or too car-specific?

Result quality

For every listing in the first run, ask the tester to classify it as one of these:

  • Would seriously consider.
  • Interesting but not actionable.
  • Wrong fit.
  • Bad data or suspicious.
  • Duplicate, stale, or already ended.

Then ask:

  • Did the "why" explanation match your taste?
  • Were the concerns useful or generic?
  • Was price, bid, time-left, and location accurate enough to act?
  • What information did you still need before clicking through?

Trust and cost

  • Do you understand who pays for AI in your setup?
  • Would you trust the app with a monthly AI cap?
  • Would you rather use owner-managed AI, your own AI account, or your own cloud agent?
  • Did any AI or automation wording feel scary, vague, or too technical?
  • Would an activity log showing exactly what the agent did make you more comfortable?

Automation feedback

Ask these only of technical testers who try the hosted MCP path.

  • Could you connect a cloud agent using the downloaded skill?
  • Did OAuth or token setup make sense?
  • Did the agent publish a run without manual API workarounds?
  • Were usage and cost events visible and understandable?
  • What failed silently?

Mobile experience

  • Were images fast enough after the first load?
  • Did swiping and reviewing feel natural?
  • Were Like, Star, Hide, and Avoid clear?
  • Did cached or offline behavior work when reception was poor?
  • What did you expect to happen after giving feedback?

Public beta readiness

  • Would you use this weekly without owner help?
  • What would need to change before you recommended it to another collector?
  • What would you pay for, if anything?
  • What feels private or sensitive?
  • What would make you delete your account?

Owner tracking sheet

For each tester, record these fields in a simple spreadsheet or Notion table:

  • Tester name, email, device, iOS version, and browser.
  • Time to onboard.
  • Invite, TestFlight, Clerk, or iOS failures.
  • Number of listings reviewed.
  • Feedback counts: like, star, hide, and avoid.
  • Run quality score from the user.
  • AI mode used and any cost incurred.
  • Whether owner intervention was needed.
  • Top three requested changes.
Treat setup friction, result trust, and cost clarity as the likely public-beta blockers. If friendly testers need owner help at any of those points, fix that before widening access.

Troubleshooting

Symptom Likely cause Fix
Friend sees invite gate after signing in Expected before accepting a Beachcar invite. Create/share the invite code from ?admin=1.
Invite code says email mismatch Invite email differs from the Google/Clerk sign-in email. Create a new invite for the exact signed-in email.
TestFlight says no build available Friend is not in the correct internal/external group, or Apple has not finished processing/review. Check App Store Connect - TestFlight - Groups and build processing status.
Run button says Budget Daily/monthly AI usage cap is exceeded or user capability is disabled. Raise caps in Preferences or use deterministic/friend-run MCP mode.
AI provider is heuristic AI Gateway credentials are missing or Gateway returned an error. Check BEACHCAR_AI_GATEWAY_* env, Cloudflare AI Gateway logs, and Run detail message.
MCP unauthorized Token missing, revoked, expired, copied with whitespace, or wrong friend token. Create a new token in the friend's Preferences and update the cloud agent secret.
Images are slow or missing on first run R2 variants are still warming, source blocked image fetch, or upstream image URL is invalid. Check admin ops image counts, Run detail source notes, and retry after warmup.
